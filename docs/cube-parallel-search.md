# 双夹爪并行搜索实验

2026-10-09 实现并测量三个两阶段主轴并行搜索。当前操作入口见[元动作搜索](cube-primitive-search.md)。此前的 A* 改进见[串行实验历史记录](cube-search-benchmarks.md)。

## 并行方式

默认最多使用三个搜索线程，每个线程探索一个不同主轴。一个线程发现更低成本的完整方案后，会更新共享上界，帮助其他线程剪枝。
求解表在每次请求开始时校验，首次完整发布后只读共享。各线程独立维护求解上下文、A* 队列和路径标签。
候选通过纯软件贴纸及机械状态重放后，才能更新最好方案。MuJoCo 对象不进入搜索线程。

`--search-threads 1` 保留串行分片；`2` 将恒等主轴单独分配给一个线程，另一个线程分时探索其余两轴；`3` 为每轴分配一个线程。
线程数还受硬件并行度和内存限制。并行时每个线程至少分得八 MiB 图预算；预算不足时减少线程，四 MiB 配置仍允许单线程。
图预算在工作线程间均分，并保守重复计算共享图；它不是进程总内存上限，不含求解表暂存、线程栈和仿真模型。

所有线程共用请求截止时间，准备阶段也计入预算。到期或异常会停止搜索，返回前等待全部工作线程退出。
只对完成评估的候选去重；受时间打断或正在评估的候选允许再次评估，避免短分片导致候选漏评。
目标仍为预计执行时间，搜索时间不加到目标中。夹爪动作仍按输出序列执行。

## 比较条件

对照是修改前冻结的提交 `03c17cb274c8fcfbdd578ddf5127e430e88540ce`。
本机为 KVM 环境，报告 AMD EPYC 9T24 和三十二个逻辑处理器。
所有性能任务依次运行，不同时运行其他基准或编译。
每次进程先运行五个边界案例，再运行十二个二十步打乱；表中只统计后十二例。
进程内缓存保留，但每次请求仍校验表文件。计时仅覆盖搜索调用，包含表准备，不含输入生成、验证和输出。
成本配置为腕速八倍、夹爪速度三十二倍，终态 `stable`，图预算六十四 MiB。

两批种子分别为 `20261009` 和 `20261010`。每种方案使用完全相同的输入和顺序。
十轮共一百七十个返回结果全部找到方案，均通过独立整数机械模型与贴纸重放；其中随机打乱为一百二十次，另有五十次边界验证。
限时调度会影响结果，因此下列单次测量不能代表所有状态或机器，也不能证明全局最优。

两批合计，一秒三线程比新版单线程平均评估约 3.06 倍候选，平均首解从 42.41 毫秒降至 22.93 毫秒。
候选计数包含排列变体，进行中的相同候选可能被不同线程评估，不等于唯一魔方面解数量。
方案成本的改善小于候选吞吐提升，不能将三倍候选数解释为三倍执行加速。

三线程一秒请求的平均调用耗时分别为 1000.20 和 1000.19 毫秒，半秒请求为 500.17 和 500.18 毫秒。
截止时间采用协作检查；线程退出、文件系统调用和系统调度可带来超时，不提供硬实时保证。

## 并发验证

候选测试通过四个回调的屏障证明枚举可以同时运行，覆盖首次并发发布、会话复用、独立异常、取消、截止时间和热缓存下的损坏文件拒绝。
机器人搜索测试覆盖冷图并发初始化、不同目标与起始姿态的同时请求、动态共享上界、运行中取消、线程参数和总图预算。
独立只读审查发现短分片占用候选可能导致漏评，已通过仅去重完成评估的候选修正；复查未发现新增实质问题。

本次候选并发程序通过 ThreadSanitizer 和 AddressSanitizer；完整机器人并发搜索测试也通过 ThreadSanitizer。
这些检测覆盖搜索与候选路径，不是整个 MuJoCo 程序的消毒器验收。
本次 `./rm test` 全部通过：二十项 C++ 测试、十九项 Rust 测试、三十四项网页与入口测试，以及四十九份文档检查。
原始日志与冻结程序保存在本机 `output/parallel-search/`，候选专用构建位于 `output/candidate-prepared-probe/`。

## 物理抽样

本次使用固定二十步打乱，三线程搜索三秒，腕速八倍、夹爪速度三十二倍。
六十个元动作成功还原，实际仿真执行 13.36810 秒。内部魔方面电机力为零，禁入接触为零，MuJoCo 警告为零。
该抽样用于验证并行输出可被现有摩擦夹爪执行，不能代表所有搜索结果的物理成功率。
日志位于本机 `output/parallel-search/physical-full20/`。

在已准备环境的仓库根目录，使用新的输出目录复现：

```bash
./rm cube --headless --dual --wrist-speed 8 --jaw-speed 32 \
  --scramble "R U2 F' D L2 B R2 F U' L D2 B' U F2 R' D B2 L' U2 F" \
  --solve --search-ms 3000 --search-threads 3 \
  --output output/parallel-physical-reproduce
```

预期命令成功结束，生成的 `verification.json` 中 `solved` 为 `true`，警告和禁入接触均为零。
失败时保留输出目录，按[故障处理](troubleshooting.md)检查；不要把软件重放成功当作物理执行成功。

## 复现方法

在 Linux 仓库根目录，先按[首次使用](getting-started.md#准备环境)执行 `./rm setup --with-tests`。
创建编译临时目录：

```bash
mkdir -p .cache/tmp
```

构建纯软件基准：

```bash
TMPDIR="$PWD/.cache/tmp" cmake --build build --target rm_cube_search_benchmark
```

创建新的结果目录：

```bash
mkdir -p output/parallel-reproduce
```

运行三线程一秒基准：

```bash
build/bin/rm_cube_search_benchmark --root "$PWD" --mode search \
  --count 12 --seed 20261009 --budget-ms 1000 --threads 3 \
  --output output/parallel-reproduce/seed20261009-t3-1000.jsonl
```

将 `--threads` 分别改为 `1`、`2`，并更换输出文件名，即可比较串行和双线程。
将种子改为 `20261010` 可运行第二批；将预算改为 `500` 可比较半秒搜索。
每次命令完成后再运行下一次，避免相互争抢 CPU。
预期退出码为零，输出包含一行元数据和十七行结果，全部 `found` 与 `verified_solved` 为 `true`。
机器较慢时，`found:false` 表示预算内没有方案，不能将其空成本按零计入平均值。
验证失败时停止性能比较；文件已存在时选择新路径，程序不覆盖已有结果。

实际使用时，在[搜索示例](cube-primitive-search.md)中加入 `--search-threads 3`；默认值已为三。
CPU 资源紧张或同时运行多个求解请求时，可设置 `--search-threads 1`。
